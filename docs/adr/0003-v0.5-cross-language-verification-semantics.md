# ADR 0003: v0.5 cross-language verification semantics

## Status

Accepted (v0.5 preparation). This ADR pins interoperability semantics; it
does not implement, vector, or refresh anything. No Go implementation, no
negative-vector fixtures, and no implementer-kit refresh belong to this
slice (issue #27).

## Context

The v0.5 gate requires a second implementation that verifies the reference
implementation's documents and vice versa, with agreement on
accept-versus-reject and a stable semantic rejection category
(`docs/V0_5_INTEROPERABILITY_PLAN.md`). The implementer brief's ambiguity
inventory lists ten open questions, several of which are classified "needs
spec clarification": the exact JCS number domain, fractional-second equality
semantics, UUIDv7 time semantics, key-validity boundary instants, and the
rejection taxonomy itself. The brief currently defers the category set to
"the second implementation's machine-readable taxonomy … until the
specification pins one".

If those boundaries were left open, the Go implementation would resolve them
itself — each choice then becoming a hidden compatibility decision that the
negative-interoperability layer could only surface after the code existed.
Pinning the semantics first keeps every cross-language disagreement
discoverable in one reviewable document, before any code or fixture
commits to one answer. This ADR and the interoperability profile
(`docs/FAW_V0_2_INTEROPERABILITY_PROFILE.md`) close that gap.

No rule in the profile contradicts the governing v0.2 specification or the
normative schemas; each decision either restates normative text or fills a
boundary the governing text leaves open (the profile records the mapping to
the brief's ambiguity inventory). The STOP-and-report rule applies if a
future change would make them contradict.

## Decision

### Why semantics are pinned before implementation

Cross-language conformance compares acceptance and stable rejection
categories, not internal structure. Every boundary that is not pinned in
advance is a boundary two implementations can disagree on silently; pinning
them here means the negative-vector layer, when it arrives, tests a settled
contract instead of discovering it. Semantics precede fixtures precede code.

### Number-domain decision

JSON numbers accepted for verification are finite IEEE-754 binary64 values.
`NaN`, `Infinity`, `-Infinity`, and negative zero are rejected.
Integer-valued JSON numbers must lie within the inclusive safe-integer
interval `-9007199254740991 … 9007199254740991`; values outside it are
rejected, never silently rounded. Larger exact numeric domains use an
explicitly defined string representation; decimal monetary ceilings remain
strings. No schema change.

### Parsed-instant timestamp comparison

Timestamps keep the existing schema lexical form (UTC, `Z`, zero or 1–9
fractional digits) and must denote valid calendar instants, not merely match
the pattern. Temporal comparisons use parsed UTC instants at nanosecond
precision, so `…00.5Z`, `…00.50Z`, and `…00.500000000Z` compare equal. The
original signed JSON timestamp is never rewritten before signature
verification or JCS canonicalization, and no non-`Z` offset is added.

### UUID opacity

UUIDv4 and UUIDv7 schema acceptance is unchanged. After syntax validation,
document IDs are opaque: no trust, ordering, expiry, or issuance time may be
derived from a UUIDv7's embedded timestamp, and that timestamp need not
match `issued_at`. Signed timestamp and sequence fields define protocol
timing and order.

### Half-open key-validity interval

A resolved key is valid for a document when:

```text
valid_from <= document.issued_at < valid_until
```

with `issued_at == valid_from` valid and `issued_at == valid_until`
invalid. No `valid_until` means no temporal upper bound from the key entry.
This pins only the interval boundaries; it does not override key status,
revocation, manifest-chain validation, trust freshness, node identity, or
`kid` binding.

### Stale trust context

Fresh/stale classification must agree across implementations; whether a
stale context is rejected or returned as a qualified result remains
disclosed local policy. A stale context never silently produces an
unqualified pass.

### Rejection taxonomy

Exactly thirteen stable semantic rejection categories are defined as
conformance-result categories (not FAW document fields):

```text
parse.invalid_json
parse.duplicate_member
parse.invalid_unicode
canonicalization.number_out_of_domain
schema.invalid
document.kind_mismatch
audience.mismatch
temporal.invalid
trust.invalid_chain
trust.unknown_key
trust.key_not_valid
signature.invalid
binding.mismatch
```

Exact exception names, messages, stack traces, and Python implementation
details need not match; reference-internal rejection-code names are not
copied merely to force equality.

### Planned negative-vector matrix

The profile documents the exact next vector slice — rejection cases N01–N15
and positive boundary cases P01–P05, each mapped to its expected category —
plus the required fixture-package contents (raw bytes, expected kind,
trust/pending/local-node context, expected accept/reject, expected
rejection category, positive-source provenance for mutations, and no
dependence on Python test files). The fixtures themselves are not created in
this slice.

### Provenance sequence

The semantics PR is merged; the reference implementation is then aligned to
it. The implementer kit is refreshed only after the language-neutral vector
package exists, because the clean-room protocol defines
`reference_material_commit` as the commit from which the Golden Vector
material was selected.

The truthful sequence is:

```text
1. semantics merged
2. reference implementation aligned
3. language-neutral negative/positive vector package merged
4. implementer kit refreshed in a separate PR
5. refreshed kit pins reference_material_commit to the durable vector-package
   merge commit
6. refreshed kit reviewed
7. only then may the separate Go repository be created
```

Vector creation and kit refresh cannot share one squash-merged PR while
truthfully claiming that the pinned `reference_material_commit` already
contains those new vectors: in a single PR the vectors first appear in the
merge itself, so no pre-existing commit contains them. A separate, later
kit-refresh PR pins the durable vector-package merge commit after it exists.

"Merge commit" means the commit that lands on `main` when a PR is merged
(for example the squash-merge SHA GitHub produces), not the branch head SHA
of the PR, which is not durable. The kit manifest's
`reference_material_commit` is updated only by the kit-refresh PR, never
invented in advance.

## Rejected alternatives

- **Resolving the ambiguity inside Go** — rejected: each un-pinned boundary
  would become a hidden per-implementation choice, and negative
  interoperability would discover disagreements only after code existed.
- **Copying Python behavior** — rejected: it would convert reference
  implementation details (including its rejection-code names) into
  normative expectations and would violate the clean-room boundary of
  ADR 0002.
- **Starting Go before negative vectors are frozen** — rejected: the
  verifier's rejection surface must be tested against a settled matrix, not
  invented while code is being written.
- **Inventing a future squash-merge SHA** — rejected: the durable
  `reference_material_commit` cannot be known until the semantics PR is
  merged; fabricating it now would pin the kit to a nonexistent commit.
- **Changing schemas without demonstrated need** — rejected: none of the
  pinned semantics requires a schema change, and altering signed-content
  shape would invalidate the kit and its vectors.

## Consequences

- This alignment slice changes reference runtime and tests only: no schema,
  vector, protocol, or version change results, and the implementer kit and
  its digests are untouched.
- The current implementer kit remains pinned to the previous reference
  material until the kit-refresh PR.
- The provenance sequence is: semantics PR → reference alignment →
  vector-package PR → kit-refresh PR → reviewed kit → separate Go
  repository (see the sequence above).
- The v0.5 gate is not complete; no second implementation exists.

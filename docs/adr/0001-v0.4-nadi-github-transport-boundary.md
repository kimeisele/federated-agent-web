# ADR 0001: Nadi/GitHub as the v0.4 second transport

## Status

Accepted (v0.4 architecture). The adapter implementation is a later issue and
PR; this record is the boundary contract.

## Context

The FAW build specification claims transport independence (governing build specification §11 and SPEC.md §7). The
only implemented transport is the offline loopback/filesystem adapter. To
make the claim credible, v0.4 must run the identical conformance suite
against a second, materially different transport.

Two candidates exist:

- **Nadi/GitHub**: the existing relay surface in the maintainer's ecosystem
  (`kimeisele/steward-federation`), a GitHub-API-backed mailbox.
- **HTTP**: a new lightweight server/client adapter built for FAW.

Inspected `steward-federation` default branch at commit
`81724edf53a9af2955ffc23974698ebbb680e332` (`nadi_kit.py`). Relevant
observed behavior:

- `NadiMessage.payload` is a dictionary;
- `NodeKeyStore` derives the NADI node identity from the public key
  (`_derive_node_id`);
- `NadiNode.process_inbox()` dispatches to registered per-operation handlers
  without any FAW-style verification gate;
- `NadiNode.sync()` clears the entire local outbox when the relay reports any
  pushed messages (`if stats["pushed"] > 0: clear_outbox()`);
- `NadiHubRelay.push_to_hub()` returns only an aggregate pushed count;
- existing deduplication keys on `(source, timestamp)`;
- `hub_repo` is configurable, though the default points to the steward relay.

## Decision

v0.4 uses **Nadi/GitHub** as the second transport. HTTP is deferred, not
rejected permanently.

The future adapter is a thin, non-normative relay wrapper around the existing
GitHub mailbox mechanics. It does not import or instantiate `NadiNode`,
`NodeKeyStore`, or `NadiTransport`. `NadiHubRelay` is treated only as a
behavior and compatibility reference.

## Why Nadi/GitHub rather than HTTP

- It already exists as a real relay surface in the maintainer's ecosystem and
  is materially different from local filesystem delivery (remote mailbox,
  network latency, duplicate reads, non-transactional multi-file writes).
- It enables a later controlled cross-account live rehearsal between
  `kimeisele` and `federation-operator` without building a hosted service.
- It proves more current project value than introducing a new HTTP service
  now: it exercises the actual transport-independence claim against a
  pre-existing, imperfect surface.
- HTTP remains a valid future adapter and is explicitly not rejected.

## FAW identity versus relay identity

Two distinct concepts:

```text
relay identity
FAW node identity
```

The relay credential / NADI sender identity exists only to publish and read
the GitHub mailbox. It must not:

- determine the FAW `node_id`;
- select the FAW signing key;
- replace manifest trust;
- authorize delegation;
- make an embedded document valid.

The embedded signed FAW document is the sole authority-bearing object.
A mismatch between relay provenance and signed-document identity may be
logged as evidence, but it must never create authority.


## Transport addressing

Three distinct concepts:

```text
FAW node identity
relay mailbox address
relay authentication credential
```

- **FAW node identity** is the stable `urn:faw:...` identity appearing in
  manifests and signed FAW documents.
- **Relay mailbox address** is the string used in the outer Nadi `source`,
  `target`, and GitHub mailbox filenames.
- **Relay credential** authenticates GitHub reads and writes but does not
  determine either FAW identity or authority.

The architecture must never assume:

```text
FAW node ID == relay mailbox address
```

They may coincide in a deployment, but the design does not require it.

Conceptual future constructor (production signature may vary slightly, but
these inputs remain explicit and separately injected):

```python
NadiTransport(
    state_root=...,
    node_id="urn:faw:local-node",
    relay_address="local-relay-address",
    routes={
        "urn:faw:remote-node": "remote-relay-address",
    },
    backend=...,
)
```

Routing rules:

1. `Transport.send(document, destination)` receives a **FAW node ID**.
2. The adapter resolves that FAW node ID through the local `routes` mapping.
3. The wrapper's `destination_node_id` remains the original FAW node ID.
4. The outer Nadi target and mailbox path use the resolved relay address.
5. Incoming mail is fetched using the local relay address.
6. The decoded wrapper's `destination_node_id` must equal the local FAW
   `node_id`.
7. A missing route fails closed and retains the staged message in the local
   outbox.
8. Route selection is local transport policy only. It cannot change the
   signed delegation target or make a document valid.
9. Relay credentials and mailbox addresses never become trust anchors.

## TransportEnvelope.source semantics

`TransportEnvelope.source` is **untrusted transport-level provenance**:

- the filesystem adapter exposes its sender transport address (which
  currently equals the sender FAW node ID);
- the Nadi/GitHub adapter exposes the outer relay source/mailbox address;
- it never exposes a trusted FAW issuer;
- the actual issuer is obtained only from the successfully verified embedded
  signed document;
- the wrapper's `source_node_id` remains an untrusted routing hint;
- a relay-source / wrapper-source mismatch may be recorded as evidence but
  can neither grant nor remove authority.

## Document-byte preservation

The adapter carries complete signed FAW documents as opaque bytes. It must
never parse, reformat, canonicalize, or mutate them in transit. Decoding the
transport encoding must reproduce the exact original bytes
(`document_sha256` detects transport corruption only; it is not a substitute
for the FAW content digest or the Ed25519 signature).

## Delivery and acknowledgement model

Per-message semantics:

- stage one exact document before remote publication;
- remove only the specifically confirmed published message from the local
  outbox;
- retain every failed or unconfirmed message;
- import remote envelopes into the local inbox by durable message ID;
- suppress already-acknowledged remote messages when the GitHub mailbox is
  read again;
- `ack()` affects one local message;
- `nack()` moves one local message to failed evidence;
- repeated remote mailbox contents are expected and safe.

The GitHub mailbox does not need to be destructively cleared for receiver
acknowledgement.

## Reuse boundary

The adapter must not inherit from `NadiNode`:

- key-derived stable node identity;
- NADI message signatures as FAW trust;
- dictionary payloads that reserialize signed FAW documents;
- handler dispatch before FAW `verify()`;
- whole-outbox clearing after partial success;
- `(source, timestamp)` as the durable message identity;
- implicit authority from NADI operation names or prompt content.

## Test strategy

One shared transport conformance suite (`tests/transport_contract.py`)
runs unchanged against every adapter. Adapter-specific setup and fault
injection live in test-harness fixtures; shared property tests never branch
on the adapter name.

The future Nadi harness must also prove:

- staged-before-publish durability;
- per-message partial failure with exact message IDs;
- repeated remote mailbox contents are idempotent;
- acknowledged messages are suppressed on re-read.

## Controlled live rehearsal

After the shared suite passes against a stubbed relay, a controlled live
GitHub rehearsal between `kimeisele` and `federation-operator` is permitted
as evidence of relay conformance. It is explicitly not an independent
external pilot and does not satisfy the v0.6 gate.

## Consequences

- The Nadi adapter stays behind the `Transport` interface.
- No FAW wire format, schema, canonicalization, signature, verification
  order, or `spec_version` change.
- The GitHub mailbox is a lab-scale compatibility surface, never a
  production bus.


## Future Nadi-specific acceptance items

The implementation PR must additionally prove:

- FAW destination resolves to a distinct relay address;
- local FAW identity and local relay address may differ;
- missing route retains the exact staged message;
- incoming wrapper addressed to another FAW node is quarantined;
- outer relay source differing from signed issuer does not affect core
  verification;
- relay credentials never appear in manifests or signed documents.

These are Nadi-specific tests and do not need to become shared filesystem
properties.

## Rejected alternatives

- **HTTP adapter now**: deferred, not rejected; a later adapter can be added
  by registering its harness in the shared suite.
- **Direct `NadiNode` reuse**: rejected — its public result model cannot
  express per-message partial success safely.
- **Hub-first relay semantics**: rejected — no destructive outbox clearing,
  no aggregate-only acknowledgement, no authority from NADI operation names.

# ADR 0002: Clean-room boundary for the v0.5 second implementation

## Status

Accepted (v0.5 preparation). This ADR defines the independence policy and the
allowed-input boundary for a second implementation. It records architecture
decisions only; no second-language code exists yet and this ADR does not
declare the v0.5 gate complete.

## Context

The roadmap's v0.5 milestone requires a second implementation written from the
specification text alone, consuming the published golden vectors, with
bidirectional interoperability against the reference implementation. The
roadmap also says the second implementation "verifies the reference
implementation's documents, and vice versa".

Two tensions need resolution before any second-language code is written:

1. What counts as "independent"? The maintainer works through AI agents; a
   second codebase the maintainer's own agent creates is not the same evidence
   class as an externally owned implementation.
2. The milestone describes a **verifier-only** implementation, but
   "verifies ... and vice versa" implies the second codebase also produces
   documents the reference must verify. A verifier-only codebase cannot
   produce signed documents without at least a fixture-signing surface.

This ADR resolves both before implementation begins so the future
implementation does not invent policy.

## Decision

The v0.5 implementation is a **verifier-focused** codebase in a **separate
repository**, built exclusively from the allowed inputs defined in
`docs/V0_5_CLEAN_ROOM_PROTOCOL.md` and shipped as the hashed implementer kit
described in `interop/v0.2/INPUT_MANIFEST.json`.

Independence is a property of who controls the codebase and what it was built
from, not of the programming language. The strict independence gate is
satisfied only by an externally owned and maintained implementation
(Class A). A maintainer-controlled clean-room implementation (Class B) is
valuable interoperability evidence and is explicitly not external
independence. Anything derived while inspecting the Python implementation or
its tests (Class C) does not count as a second implementation at all.

## Independence classes

### Class A — independent external implementation

Created and maintained by a person or organization not controlled by the FAW
maintainer. Built from the implementer kit without access to the Python
source. Satisfies the strict v0.5 independence gate after bidirectional
interoperability passes.

### Class B — maintainer-controlled clean-room implementation

Created in an isolated workspace from the implementer kit by an agent or
toolchain the FAW maintainer controls, with no access to the Python source,
tests, or runtime. Useful second-codebase and interoperability evidence.
Must be disclosed as maintainer-controlled. Does not by itself satisfy the
strict roadmap or v1.0 independence claim.

### Class C — port or derived implementation

Created while inspecting, translating, or adapting Python runtime or test
code. Does not count as a second independent implementation under any
labeling.

"Independent" is never redefined to mean only "another programming
language". A Go translation of the Python source is Class C evidence, not
independence.

## Target language

Go is the default v0.5 implementation language because it provides a
materially different runtime and toolchain, standard-library SHA-256 and
Ed25519, straightforward standalone CLI distribution, and useful pressure on
JSON parsing, JCS, and schema assumptions.

This is reversible before implementation when a genuinely external
implementer requests TypeScript. The default does not bind an external
implementer.

## Repository boundary

The future implementation MUST live in a separate repository. It MUST NOT be
added under `implementations/go/`, `go/`, or `second-implementation/` inside
`federated-agent-web`.

The separate repository MUST NOT share with the Python reference
implementation:

- source files;
- test helpers;
- generated code;
- packages;
- build tooling;
- runtime dependencies.

The repository is not created in this task.

## Allowed reference inputs

The implementer kit allowlist is fixed in `docs/V0_5_CLEAN_ROOM_PROTOCOL.md`
and machine-enforced by `interop/v0.2/INPUT_MANIFEST.json` and
`scripts/build_v0_5_implementer_kit.py`. It contains only:

- `SPEC.md` — summary; conflicts lose to the governing specification;
- `docs/federated-agent-web-build-spec-v0.2.md` — governing where it
  contains normative requirements;
- `schemas/**` — normative machine-readable constraints;
- `vectors/**` — conformance fixtures;
- `SECURITY.md` — non-normative guidance;
- `docs/V0_5_IMPLEMENTER_BRIEF.md` — non-normative guidance;
- `interop/v0.2/INPUT_MANIFEST.json` — the kit manifest.

`LICENSE` is listed in the original allowlist draft; the repository at
`bb85221` ships no license file (`pyproject.toml` declares MIT metadata).
Until a license file is published, the kit omits `LICENSE` and this is
recorded as a candidate erratum for the operator rather than guessed.

## Forbidden reference inputs

The kit MUST NOT contain:

- `src/**`, `tests/**`, `examples/**`, `.github/**`, `scripts/**`,
  `pyproject.toml`;
- `docs/IMPLEMENTATION_REPORT.md`, `docs/REUSE_REPORT.md`,
  `docs/TRACEABILITY_V0_2.json`, `docs/TRANSPORT_CONFORMANCE.md`,
  `docs/NADI_LIVE_REHEARSAL.md`, `docs/ADAPTER_NADI.md`;
- Python filenames, Python bytecode, coverage output, test node IDs;
- reference rejection-code implementation details or reference package
  imports;
- Git history, `.git/`, local paths, credentials;
- private keys other than the fixtures explicitly labelled TEST-ONLY in the
  published Golden Vectors.

The test-only vector key material is public fixture material, not a
deployment identity. It exists so an independent implementer can reproduce
signatures; it grants no real-world authority.

## Dependency policy

The second implementation MUST NOT import, invoke, or copy from the Python
reference implementation or any of its packages, including its JCS and
crypto dependencies. It may use the Go standard library and independent
third-party libraries. Where the governing specification names a maintained
JCS implementation for Python, that is guidance about the reference, not a
requirement that the second implementation use the same library.

The implementer kit build tooling uses only the Python standard library and
performs no network operation.

## Interoperability model

Bidirectional interoperability is layered:

- the Go verifier verifies the committed Python reference fixtures
  (manifests, delegation, receipt, canonicalization, digest, and signature
  vectors);
- the Go codebase includes a deterministic **conformance fixture emitter**
  that produces new test-only signed fixtures;
- the Python reference verifies the emitted fixtures with its public
  verification interface.

The acceptance comparison is accept-versus-reject plus a stable semantic
rejection category. Exact human-readable wording, internal implementation
structure, and call stacks are not required to match.

## Reverse-direction evidence

The v0.5 implementation remains verifier-focused. It may include a
deterministic **conformance fixture emitter** as the minimum reverse-direction
surface. The emitter:

- is not a node, transport, executor, or production signing service;
- exists only to produce test-only signed manifest, delegation, and receipt
  fixtures plus artifact digest metadata;
- never uses a deployment private key.

If this interpretation conflicts with a normative requirement, a spec
erratum issue is opened rather than silently deciding. The emitter is not
implemented in this task.

## Specification errata process

Ambiguities and contradictions found during implementation are reported as
spec erratum issues against `docs/federated-agent-web-build-spec-v0.2.md`.
An erratum is opened when a genuine contradiction is demonstrated; open
questions that are merely unclear are listed in the implementer brief's
ambiguity inventory until implementation pressure decides them. No behavior
is copied from the Python source to resolve an ambiguity.

## AI-agent disclosure

The future implementation report MUST disclose:

- whether an AI agent was used;
- which exact input kit (manifest digest) it received;
- whether it had network access;
- whether it had any access to the reference repository;
- whether its operator or repository is controlled by the FAW maintainer.

AI use does not automatically invalidate independence. Access to the Python
implementation or its tests does invalidate the clean-room claim.

## Consequences

- The v0.5 gate is not complete until a second implementation exists and
  bidirectional interoperability passes; this ADR alone closes nothing.
- Class B evidence is possible without an external operator and is planned
  as the fallback, labeled exactly as maintainer-controlled.
- The spec, schemas, vectors, protocol, and version are unchanged by this
  ADR.
- No Go or TypeScript code is written in this slice.

## Rejected alternatives

- **Second implementation inside this repository** — rejected: it would
  share tooling and history and make the clean-room boundary untestable.
- **"Independent" defined as any second language** — rejected: a direct
  translation is derived work and must not satisfy the strict gate.
- **Requiring the second implementation to be a full node** — rejected: the
  milestone is verifier-only; local stateful admission is represented by
  explicit input fixtures documented in the implementer brief.
- **Silently resolving verifier-only versus reverse interoperability** —
  rejected: the fixture-emitter boundary is recorded here so it is a
  documented decision, not a guess.
- **Publishing the Python test suite to the implementer** — rejected: it
  would destroy the clean-room claim.
